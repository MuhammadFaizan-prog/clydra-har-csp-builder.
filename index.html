    How it works

    From DevTools to a deployable header in four moves

    1. Record the flows that matter

      Open DevTools → Network, tick Preserve log, then sign in, browse and check out the way a real visitor would.

    2. Export and load the HAR

      Right-click the request list → Save all as HAR. Load one file or several; recordings are merged into one policy.

    3. Review each source

      Every origin the pages used is listed under the directive it needs, with the requests behind it. Exclude anything you don't trust.

    4. Ship Report-Only, then enforce

      Copy the header in Report-Only mode, watch for violation reports, then switch to Enforce when the reports go quiet.

    HAR
    HTTP Archive: a JSON file of every request your browser made while DevTools was recording.
    Directive
    One rule in the policy, such as script-src for JavaScript or img-src for images.
    Source
    Where a directive allows loading from: 'self' (your origin), a host such as https://js.stripe.com, or data:.
    Report-Only
    The browser reports what the policy would block without blocking anything. The safe first deployment.

    Privacy

    The recording stays in your tab

    • The HAR file is read with the browser's File API. There is no server, account or upload.
    • Only request URLs, methods, status codes, request types and your own pages' HTML are kept in memory. Cookies, auth headers and other response bodies are not copied out of the file.
    • The builder ships its own strict policy (connect-src 'self'), so the page itself cannot send data to another host. The only request it makes is for the sample file, from this site.
    • Nothing is stored. Reloading or closing the tab clears the recording.

    Limits

    What a recording can't tell you

    • A HAR only covers the flows you clicked through. Pages, roles and features you didn't visit are missing from the policy.
    • Inline scripts are hashed only when the HAR includes page content. Scripts that change on every load need server-generated nonces instead.
    • Inline event handlers (onclick=) and style="" attributes are reported, not allowed. Move them into files or classes.
    • Sources are host-level. The builder does not narrow them to paths or generate 'strict-dynamic' policies.

    FAQ

    Practical questions

    Which files can I load?

    Standard HAR files from Chrome, Edge or Firefox DevTools, or any tool that writes HAR. Up to 40 MB per file. Load several to merge recordings of different flows into one policy.

    How does it decide which directive a request needs?

    In order of trust: the browser's own Sec-Fetch-Dest header, Chromium's recorded resource type, the response MIME type, then the file extension. Anything still unknown falls back to connect-src. Browser-extension requests and CORS preflights are ignored.

    Is the generated policy safe to enforce straight away?

    Treat it as a draft. It allows what the recording saw, nothing more, so a flow you didn't record will break under enforcement. Deploy it as Content-Security-Policy-Report-Only first and add a report URL to see what it would block.

    Which export formats are there?

    A raw HTTP header, Nginx add_header, Apache Header always set, a vercel.json headers block, a Netlify _headers file, and an HTML <meta> tag. The meta tag can't carry frame-ancestors or report-uri and can't be report-only; the builder removes those and says so.

    Does my HAR file contain secrets?

    It can: cookies, tokens and form data are often recorded. This builder reads it locally and keeps only the fields listed under Privacy, but treat the file itself as sensitive and delete it when you're done.
